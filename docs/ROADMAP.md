# AetherRenju 路线图

> v0.1 的定位:**规则正确、能下、代码简单**。禁手判定与独立暴力判定器
> 在随机局面上逐点对拍一致,搜索和评估都是第一版,刻意没有堆技巧。
> 下面按「先补齐棋力缺口 → 再增强搜索 → 再升级评估」排优先级,
> 每一项都写清楚**验收方法**,不做完不算完。

现状基线(本机 Node 22,桌面级 CPU):安静中盘局面约 **20-29 万节点/s**,
预算内稳定走完 2~4 层;引擎 chunk gzip 约 11 KB(**预算 35 KB**,与国际象棋 /
中国象棋引擎同档)。

本路线图**只覆盖引擎本身**:WebOS 应用侧(棋谱、复盘、3D 视图等)不在此列。

---

## P0 —— 棋力骨架(同样的预算下多看 2~3 层)

1. **PVS(主变搜索)**:全窗口搜第一个着法,其余用零窗口试探,失败再重搜。
   几乎是纯赚,先做。
   - 验收:`bench.mjs moves` 同深度评分不降,节点数下降 20%+。
2. **空着裁剪(null move)**:五子棋没有「被迫应将」概念但被迫挡四是常态;
   在对方存在成四点时禁用空着,其余局面 R=2 试探。
   - 验收:固定深度节点数下降且对拍最佳着法不系统性变差(自对弈胜率 ≥50%)。
3. **aspiration window**:上一层分数 ±窗,失败再全开,减少迭代加深的全窗口浪费。
4. **置换表深度优先替换**:目前总是替换,改为「深度优先 + 世代计数」,
   深层着法信息活得更久。

## P1 —— 战术与规则深化

1. **VCT(威胁空间搜索)**:静态搜索目前只有「四」的强制链(VCF),
   把「活三」也纳入强制序列可以看穿两层叫杀。注意与禁手交互:
   黑方的三要按「真三」判定(补点合法才成立)。
   - 验收:构造双杀/反杀测试局面,引擎不再走出必败挡法。
2. **禁手增量化**:禁手判定目前懒判定 + 小缓存,长搜时仍是热点;
   维护「每个点是否可能禁手」的位图(随走子局部失效),把搜索内的
   判定次数压到必要最少。
   - 验收:`bench.mjs forbidden` 吞吐提升 3 倍以上,对拍仍逐点一致。
3. **和棋判定**:满盘和棋已处理;60 手无进展(双方无四以上威胁)判和可避免
   无限空转(对人类几乎不可见,对自对弈调试有用)。

## P2 —— 评估升级

1. **精确棋型评估**:五元窗计数是「软」评估,活三/眠三的分辨靠窗重叠;
   改为逐线扫描分类棋型(连五/活四/冲四/活三/眠三/活二……)并按方计分。
   - 验收:自对弈 A/B(新评估 vs 旧评估,同预算)胜率 ≥55%。
2. **Texel 调参**:评估参数目前全是手调;用自对弈局面集做 qpst 调参。
3. **位置加成**:先手方天元价值、靠边衰减,目前完全没有。

## 明确不做(已拍板,不是「还没做」)

- **开局库 / 残局库** —— 不内置任何着法表
- **RIF 26 开局规则 / swap 体系** —— 只做自由开局 + 禁手
- **UCCI/Gomocup 协议对接** —— 不与第三方引擎对打;棋力只靠自对弈 A/B 定方向
- **多线程** —— 单线程到底
- **WASM** —— 暂未启动,等 JS 侧优化到头再评估
